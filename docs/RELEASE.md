# Release Guide

## Purpose

Production release process for Overlay Monster.

## Versioning

Use Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

GitHub tags must use:

```text
vMAJOR.MINOR.PATCH
```

Example:

```text
v0.2.9
```

## Development vs Release

Normal commits to `main` run CI only.

A Windows release runs only when a semantic version tag is pushed, or when the release workflow is manually dispatched with a matching version.

```text
Code commit
   ↓
CI
   ↓
No release

Version + tag
   ↓
Release workflow
   ↓
Windows installer + latest.yml
```

## Before Release

Run:

```bash
npm install
npm run typecheck
npm run build
npm run dist:win
```

Check:

- `package.json` version.
- `electron-updater` compatibility.
- Electron startup.
- Capture protection status.
- Auto-update configuration.
- Installer generation.
- `latest.yml` generation.

## Git Release

Preferred flow:

```bash
npm version patch
git push origin main --follow-tags
```

This creates the version commit and semantic version tag.

Example:

```text
0.2.8 → 0.2.9
        ↓
      v0.2.9
        ↓
Release workflow
```

If creating the tag manually:

```bash
git tag v0.2.9
git push origin v0.2.9
```

`package.json.version` must exactly match the tag version.

## GitHub Release Artifacts

A successful Windows release must contain:

- `Overlay-Monster-Setup.exe`
- `latest.yml`
- Any NSIS metadata/blockmap files generated by electron-builder.

The release must be marked as the latest stable GitHub release.

## Auto-Update

Test with two versions:

```text
Installed: 0.2.8
Published: 0.2.9
```

Do not test auto-update by reinstalling the same version.

The installed app checks GitHub Releases through `electron-updater`, downloads the newer installer, and restarts into the new version.

## Vercel Download

The web download button should use:

```text
/releases/latest/download/Overlay-Monster-Setup.exe
```

Do not hard-code a historical version.

## Dependency Reproducibility

`package.json` uses exact versions for build-critical packages.

`package-lock.json` is maintained by `.github/workflows/sync-lockfile.yml`.

Release and CI workflows use `npm ci` when the lockfile exists.

## Failure Handling

1. Open the failed workflow.
2. Find the first failing step.
3. Read the actual error.
4. Identify the root cause.
5. Fix the configuration or code.
6. Add a reusable lesson to `docs/DEVELOPMENT_LEARNINGS.md`.
7. Run CI.
8. Create a release tag only after CI passes.

Do not blindly retry a failed release.
