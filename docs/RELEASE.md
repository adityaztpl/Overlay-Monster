# Release Guide

## Purpose

This document defines the production release process for Overlay Monster.

## Versioning

Use Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

Examples:

```text
0.2.3
0.2.4
0.3.0
1.0.0
```

The GitHub release tag must match:

```text
v0.2.4
```

## Release Flow

```text
Update package.json version
        ↓
Validate build
        ↓
Create semantic version tag
        ↓
Push tag
        ↓
GitHub Actions
        ↓
Windows NSIS installer
        ↓
GitHub Release
        ↓
latest.yml
        ↓
electron-updater
```

## Before Release

Run locally when possible:

```bash
npm install
npm run typecheck
npm run build
npm run dist:win
```

Check:

- Application version.
- Installer generation.
- Electron startup.
- Auto-update configuration.
- GitHub publish configuration.

## Git Release

Example:

```bash
npm version patch
npm push origin main --follow-tags
```

If creating the tag manually:

```bash
git tag v0.2.4
git push origin v0.2.4
```

## GitHub Release Artifacts

A successful Windows release should contain:

- `Overlay-Monster-Setup.exe`
- `latest.yml`
- Any required NSIS metadata/blockmap files generated by electron-builder.

## Auto-Update Requirements

The installed application must be older than the published version.

The GitHub release must contain valid update metadata.

The updater must be able to reach the GitHub release provider.

Never test auto-update by repeatedly reinstalling the same version. Use two distinct versions, for example:

```text
Installed: 0.2.3
Published: 0.2.4
```

## Vercel Download

The web download button should point to the latest GitHub release installer rather than a hard-coded historical version.

Preferred pattern:

```text
/releases/latest/download/Overlay-Monster-Setup.exe
```

## Failure Handling

When a release workflow fails:

1. Open the failed job.
2. Find the first failing step.
3. Read the actual error.
4. Fix the root cause.
5. Commit the fix.
6. Re-run the workflow only after checking the changed configuration.
7. Add a lesson to `docs/DEVELOPMENT_LEARNINGS.md` if the failure reveals a reusable rule.

Do not fix release failures by blindly retrying the same workflow.
